# FRAMPP v0.8.0 集成 caddy-panel 评估

> 状态：评估稿（2026-09-06，未实施）
> 对象：本地项目 `C:\work\workspace\caddy-panel\panel-dev`（v0.8.0，发布包
> `.tools/caddy-panel-v0.8.0.zip`，SHA-256 待发布时固化）
> 关联：`docs/0.8.0-plan.md` 第 10 项

## 1. 结论摘要

- caddy-panel v0.8.0 与 FRAMPP 的契合度很高：**纯 PHP、零第三方运行时依赖**
  （无 composer / vendor / Node / Go），SQLite 存元数据，cURL 直连 Caddy
  Admin API（TCP 与 unix socket 双支持），站点以 `caddy.d` 片段落盘并走
  `/adapt` → `/load` 双校验 + 快照回滚——与 FRAMPP §2.11 既定的“PHP 原生 +
  admin API + 文件式配置”路线一致，不推翻先前的第三方面板否决决策。
- **推荐 v0.8.0 采用“并存过渡”**：caddy-panel 作为新模块 `modules/caddy-panel`
  随包安装并接管管理入口，完整提供站点 / Caddyfile / 证书 / 日志管理；服务
  启停、状态与 IP 访问控制等“平台能力”暂留在现控制面板（可迁到独立过渡端口），
  迁移完成前不删除旧界面。
- 最大集成点是 **Caddyfile 归属权迁移**：caddy-panel 会把主 Caddyfile 整体
  重写为 `global.caddy + import caddy.d/*.caddy`，FRAMPP 现模板中硬编码的
  8080 / 8081 站点块与 access-filter import 必须先迁成片段 / 全局块，否则会被
  覆盖。init / 升级流程需要“首启用旧模板引导 → caddy-panel 交接 → doctor 自检”
  的过渡与回滚路径。

## 2. 双方现状核对

| 维度 | FRAMPP 现控制面板 | caddy-panel v0.8.0 |
| --- | --- | --- |
| 实现 | PHP（无前端框架，原生页面） | PHP 8.1+（自研路由 / autoload，无 composer）+ Vue 3（预构建到 `public/`） |
| 数据 | `var/runtime.json`、`var/secrets.json` | SQLite `var/panel.sqlite`（WAL）+ 快照 `var/backups/config/` + `var/sessions/` |
| 配置源 | `etc/Caddyfile`（模板生成）+ `etc/caddy.d/*.caddy` + `etc/access-filter.caddy` | `etc/global.caddy` + `etc/caddy.d/*.caddy`（可指向任意绝对路径） |
| Caddy 交互 | `CaddyAdminClient`（TCP / unix） | `AdminClient`（cURL，TCP / unix via `CURLOPT_UNIX_SOCKET_PATH`） |
| 热重载 | 保存片段后组装并 POST `/load` | `/adapt` 预校验（行号错误）→ `/load`，失败自动回滚 + last-good |
| 认证 | 本机 8081 + `panel_token`（写操作） | 本地 `REMOTE_ADDR=127.0.0.1/::1` 免认证；远程单管理员 + 限速 + CSRF |
| 功能 | 服务启停 / 状态 / 孤儿清理 / 端口 / 传输模式 / IP 访问控制 / 站点 CRUD / 项目创建 | 仪表盘 / 站点（static / reverse_proxy / php）/ Caddyfile 三层编辑 / 证书 / 日志 / 快照恢复 / 设置 |
| 依赖扩展 | FrankenPHP 内置 PHP | `pdo_sqlite` / `openssl` / `curl` / `zip`（FRAMPP 两端构建均含） |

caddy-panel 自身的 `docs/caddy-webui-plan.md` §9 已写明“先服务 FRAMPP、
作为 `modules/control-panel` 的演进版本”，通过 `config.php` 适配
（caddy.d 目录、access-filter 有无、php 形态、认证、Admin API 地址），
因此集成方向有设计依据。

## 3. 集成目标与非目标（v0.8.0）

目标：

- caddy-panel v0.8.0 随 Windows / Linux / Docker 安装包分发，安装为
  `modules/caddy-panel/`；
- 提供 Web 管理界面：站点 CRUD、Caddyfile 校验与热重载、快照回滚、证书、
  日志；本地 127.0.0.1 免认证，sock 模式下经 unix socket 连接 Admin API；
- 中英双语、界面与 CLI 语言规则与 caddy-panel 现状一致；
- 现服务启停 / 状态 / IP 访问控制保持可用（并存期挂在过渡地址）。

非目标（后续版本）：

- 不删除现控制面板、不迁移 ServiceManager / IP 访问控制进入 caddy-panel；
- 不改动 caddy-panel 内部实现（仅通过 `config.php` 与目录映射适配；若发现
  必须的小增强，作为 caddy-panel 独立项目的变更另行评估）；
- 不引入多用户 / 集群 / 站点备份调度等 P1/P2 能力。

## 4. 布局与打包映射（草案）

caddy-panel 采用“webroot + APP_ROOT”两区域布局，FRAMPP 内映射为：

```text
modules/caddy-panel/
├─ public/                  # webroot：index.php / install.php / assets（由 FrankenPHP 提供）
├─ src/ php/                # APP_ROOT：应用源码
├─ etc/                     # APP_ROOT：global.caddy、caddy.d 种子、installed 标记
├─ var/                     # APP_ROOT：panel.sqlite、backups、sessions、logs
├─ bin/panel                # APP_ROOT：CLI（passwd / setup / snapshot / restore / doctor）
└─ config.php               # APP_ROOT：由 FRAMPP init 生成
```

- `public/panel.bootstrap.php` 的 `APP_ROOT` 由 init 直接写为
  `modules/caddy-panel` 绝对路径；
- `config.php` 由 init 生成：
  - `caddy.admin_api`：TCP 模式 `http://127.0.0.1:2019`；sock 模式
    `unix://<FRAMPP_HOME>/var/run/admin.sock`（与 `runtime.json` 联动）；
  - `caddy.caddyfile` / `caddy.fragments_dir` / `caddy.global_file`：
    指向 FRAMPP 真实 `etc/Caddyfile`、`etc/caddy.d/`、`etc/global.caddy`
    （保证 caddy-panel 管理的就是 FrankenPHP 实际加载的配置）；
  - `caddy.log_file`：指向 `logs/frankenphp-access.log`（日志页可用）；
  - `auth.allow_local_auto_login`：默认 true（与 FRAMPP localhost 安全基线一致）。
- 打包：Windows `setup.iss` / Linux `build-linux-package.ps1` 将
  `caddy-panel-v0.8.0.zip` 解压进 staging 的 `modules/caddy-panel`，zip 校验
  SHA-256（遵守供应链规则）；Docker 复用 `.run` 载荷自动携带。

## 5. Caddyfile 归属迁移（核心方案）

现状：`init` / `AccessManager` 用 `Caddyfile.template` 生成主文件，其中
`http://127.0.0.1:8080`（默认站点）与 `http://127.0.0.1:8081`（控制面板）
硬编码，`{{ACCESS_IMPORT}}` 导入 access-filter，`{{CADDY_D}}` 导入用户站点。

目标：主 Caddyfile 由 caddy-panel 组装（`global.caddy` + `import caddy.d/*.caddy`）。

迁移步骤（草案）：

1. 首次 init 仍用现有模板生成“引导 Caddyfile”，保证 8080 站点与 caddy-panel
   自身可访问；
2. init 同时生成移交素材：
   - `etc/global.caddy`：`{ frankenphp; admin <addr>; auto_https off }`
     （含 Souin 注释等模板全局内容）；
   - `etc/caddy.d/00-default.caddy`：默认站点块（htdocs 8080，含 access-filter
     import 指令）；
   - `etc/caddy.d/01-panel.caddy`：caddy-panel 自身站点块
     （`root * modules/caddy-panel/public` + `php_server` / `php`+`file_server`
     待与 FrankenPHP 指令实测对齐）；
3. 调用 caddy-panel 初始化（见 §6）完成 `config.php`、`var/installed` 与管理员，
   随后由 caddy-panel 组装并 `/load` 新 Caddyfile —— 交接完成；
4. 交接后：
   - `AccessManager` 不再整体渲染 Caddyfile，只维护 `access-filter.caddy`
     片段内容并保留模块级 `/access-filter/reload`；
   - 站点管理默认走 caddy-panel；现有 `web/sites.php` 在并存期改为引导页
     （或标记只读），避免两处写 `caddy.d` 冲突；
   - 现控制面板（服务 / IP 访问）迁移到过渡监听端口（见 §7）。
5. 恢复兜底：FrankenPHP 启动前由 `bin/panel doctor --fix` 自检（systemd
   `ExecStartPre` 与 Docker entrypoint 示例 caddy-panel 已提供）；配置损坏时
   回滚 last-good，init / 升级脚本保留“回到旧模板 Caddyfile”的手动开关。

## 6. 初始化与升级流程

- **全新安装（v0.8.0）**：init 解压模块 → 生成 `config.php` 与移交素材
  （global / 片段种子）→ 引导 Caddyfile 先保证 caddy-panel 可达 → 完成
  caddy-panel 初始化（管理员与 `var/installed`）→ 组装新 Caddyfile 并热加载
  → doctor 自检。
- **存量升级（0.7.x → 0.8.0）**：保留现 `etc/Caddyfile`、`etc/caddy.d/` 与
  `var/` 不动；新模块以并存入口上线（见 §7 方案）；caddy-panel 首次初始化时
  把现有用户站点 `caddy.d` 片段导入站点库，之后再决定是否切换主 Caddyfile
  归属；提供“回退到旧模板 Caddyfile”开关。
- **数据保留**：caddy-panel 的 `modules/caddy-panel/var/`（sqlite / 快照 /
  会话）与 `config.php` 在升级 / 卸载时按模块策略处理（卸载询问保留或删除）。

## 7. 管理入口与端口策略（待选）

三个候选：

- 方案 1（推荐）：caddy-panel 接管管理端口 8081（单一管理入口）；现控制面板
  的“服务 / IP 访问”功能迁到过渡端口（如 8082），README / 安装器图标 /
  健康检查引用同步更新。用户心智最清晰，代价是 8081 语义变化。
- 方案 2（低风险并存）：现控制面板保持 8081 不动，caddy-panel 另开端口
  （如 8083）作为 Caddy 管理界面；两个管理入口并存，改动最小，但入口分散。
- 方案 3（完全替换，v0.8.0 不做）：直接删除现控制面板并以 caddy-panel 全量
  替代（服务管理缺失，风险高）。

> 注：端口号同时受第 7 项（8080/8081 冲突调研）影响，正式定案时一并决策。

## 8. 认证与安全衔接

- 本地免认证依赖 `REMOTE_ADDR` 判定；FRAMPP 默认仅绑定 127.0.0.1，Caddy
  直连时判定成立。若用户自定义监听 / 前置反代，需按 caddy-panel 文档配置
  `trusted_proxies`，或退回单管理员密码登录（内置限速 + CSRF）。
- caddy-panel 的 `config.php`、`var/`（sqlite / sessions / 备份）必须位于
  webroot 之外——模块布局已保证 `public/` 是唯一 Web 暴露目录，init 需校验。
- 并存期现控制面板的 `panel_token` 机制保持不变；后续把“平台服务管理”并入
  caddy-panel 时再统一认证与 Token（含 Agent / API Token 演进）。

## 9. 依赖与体积核查

- PHP 扩展：`pdo_sqlite`（PDO sqlite）、`openssl`、`curl`、`zip` 在 FRAMPP
  Windows / Linux 内置 FrankenPHP 扩展清单中均存在（PHP 8.5.9），满足要求；
- 无 composer / vendor / Node 运行时依赖；前端为预构建静态产物；
- 发布包 zip ≈ 600 KB，解压后 `public/` 资源 ≈ 1.7 MB，对安装包体积影响很小；
- Vue 使用 history 路由，服务站点需 `try_files` 回退到 `index.php`
  （FrankenPHP `php` + `file_server` 已满足，与 caddy-panel 站点表单的
  `php_server` 形态需实测对齐一处小差异）。

## 10. 风险与待决问题

- **主 Caddyfile 归属切换**是最高风险点：迁移顺序、失败回滚、旧安装（0.7.x）
  升级时的存量 `etc/Caddyfile` 与用户自定义站点必须保留且可回退；
- caddy-panel 初始化可否**非交互**完成（FRAMPP init 需要）：`install.php`
  首次访问创建管理员；FRAMPP 安装器为静默流程，倾向 init 生成一次性
  `setup_token` + 预置 `var/installed` / 管理员记录，或要求 caddy-panel 的
  `bin/panel setup` 支持参数化——列为与 caddy-panel 项目协调的小增强；
- access-filter 与 FRAMPP 固定站点的表示：全部可转 `caddy.d` 片段 / global，
  但“面板自身站点”与“默认站点”由谁声明、升级时是否可被用户误删，需要约定
  （建议保留在 `caddy-panel` 管理的站点库内并标 `managed`，或锁定前缀文件）；
- 端口与入口策略（§7 三选一）、与第 7 项端口冲突调研的联动；
- 卸载 / 升级时 `modules/caddy-panel/var`（sqlite / 快照）与 `config.php`
  的保留策略。

## 11. 建议的 v0.8.0 实施范围

- P0：模块随包安装与 init 生成 config（含 sock/tcp 双模式）；caddy-panel
  界面可访问；站点 CRUD / Caddyfile 校验热重载 / 快照恢复可用；doctor 接入
  启动自检；升级路径保留存量配置并可回退。
- P1：证书 / 日志页走通；旧站点管理页引导至新界面；入口端口策略定案。
- 后续：ServiceManager / IP 访问控制以页面或 API 形态并入 caddy-panel；
  再评估是否退役现控制面板。

## 12. 待办（评估后）

1. 与 caddy-panel 项目核对两处小增强：非交互初始化（setup token / CLI
   参数化）、站点形态 `php_server` vs `php`+`file_server` 的模板选项；
2. 在 FRAMPP 侧以独立模块做一次真机冒烟（Windows + Linux + sock 模式）；
3. 定案后在本蓝图补决策记录，并把第 10 项从“候选”改为“已定案”。
