# FRAMPP v0.8.0 改进计划

> 状态：计划中（2026-09-01）
> 基线：v0.7.1
> 更新：2026-09-03 追加第 8、9 项（caddy-exec / caddy-timer）
> 说明：记录 9 项改进（第 1–8 项面向 v0.8.0，第 9 项 caddy-timer 为后续版本 backlog）；实施前按仓库规则在 `docs/blueprint.md` 补决策记录。

## 改进清单

| # | 改进项 | 现状 | 计划方案 |
| --- | --- | --- | --- |
| 1 | README 全部并入 docs、docs 全部并入 share，并补齐中文版 README | Linux 安装包根目录含 `README.md`（仅英文）、`docs/`（仅 `docs/user/*`）、`VERSION`、`LICENSE`；Windows（`setup.iss`）同样只分发英文 `README.md`（`isreadme`）与 `docs/`；**`README.zh-CN.md` 两个平台均未随包分发** | 安装包根目录不再放 `README.md` / `docs/`，文档统一收进 `share/docs/`：`share/docs/README.md`（英文）、`share/docs/README.zh-CN.md`（中文，补齐）、`share/docs/user/*`（docker / upgrade 等）；README 内容全部并入 docs，仓库根 README 仅作入口/索引，安装包内不再重复 |
| 2 | `frampp start`（TCP 模式）检查端口占用，能判断启动失败 | `ServiceManager::start()` 仅检查服务自身 PID；`startDetached()` 用 `proc_open` 拉起进程后立即返回 PID，不验证端口是否监听成功。TCP 模式下端口（8080 / 8081 / 3306 / 6379 / 2019）被其他进程占用时服务绑定失败，但 `frampp start` 仍返回 `started=true`，用户无法判断启动失败 | 启动前（TCP 模式）预检目标端口（http / panel / mysql / redis / Caddy admin 2019）：端口已开放且非 FRAMPP 自身服务则返回明确错误（含占用提示与建议：`frampp ports` / 换端口）；sock 模式检查 `var/run/*.sock` 占用。启动后轮询端口 / socket 就绪（超时约 10s），结合日志尾部判定结果：就绪 → `started=true`；超时或进程即退 → `started=false` + error（附日志末行），CLI 退出码非零 |
| 3 | VERSION 放入子目录（`etc/`） | Linux 安装包把仓库根 `VERSION` 复制到安装根目录 `VERSION`；`bin/frampp version` 从 `<root>/VERSION` 读取。Windows 安装包根目录无 VERSION（版本号经 `release-defines.iss` 注入） | 安装包内 `VERSION` 移入 `etc/VERSION`（仓库根 `VERSION` 保留，作为构建输入与 CI 读取源）；`self_version()` 读取顺序改为 `etc/VERSION` → 旧 `<root>/VERSION` 兼容回退 |
| 4 | 安装脚本提示语统一中英双语 | 部分安装 / 初始化 / 卸载脚本的输出仍仅显示中文，未对齐 v0.6.0 定下的“安装提示统一中英双语”约定 | 排查安装、初始化、卸载流程中的纯中文提示并统一为中英双语；涉及 `installer/scripts/init.ps1`、`installer/scripts/linux/init.sh`、`installer/scripts/linux/frampp-installer.sh`、`bin/uninstall`、`installer/setup.iss` 文案等 |
| 5 | 新增 `frampp restart` 指令 | CLI 只有 `start` / `stop`，缺少 `restart` | 新增 `frampp restart [service]`（默认 `all`）：等价 stop + start，依赖顺序沿用 stop 的反序（先数据服务后 Web）；控制面板（`web/action.php`）与 `framppd` 同步支持；tcp / sock 模式下行为一致 |
| 6 | `frampp start` 启动失败延迟检测 | 服务启动失败无法立即感知：进程拉起后即返回，可能误报 `started=true`，用户要等报错/连接失败才发现 | 启动后延迟轮询（约 1s×10 次，可配置）验证服务真正就绪：进程存活 + 端口 / socket 可连接 + 日志无致命错误；超时或进程即退 → `started=false` + error（附日志末行），CLI 退出码非零；与第 2 项（启动前端口预检）配套实施，合称“启动前预检 + 启动后就绪检测” |
| 7 | 缺省监听端口 8080 / 8081 易冲突，调研更优方案 | 默认站点端口 8080、控制面板 8081（另有 Caddy admin 2019、MySQL 3306、Redis 6379），与常见本机服务（Nginx / Apache / IDE / 容器端口映射等）容易冲突；当前无自动规避机制 | 调研更优默认值或动态端口策略，候选：安装 / 首次 `init` 时检测端口占用，冲突则自动顺延或分配首个空闲端口并写入 `runtime.json` 的 `ports`；对外端口改用高位段（如 18080 / 18081）；保留 `frampp ports` 查看与控制面板展示实际端口；Caddyfile 生成、ServiceManager、init 脚本、文档说明全部跟随配置 |
| 8 | 引入 `caddy-exec`：Caddy 启动 / 退出时自动拉起与回收 mysql、redis，简化启动脚本 | 目前安装器、`frampp start all`、`framppd`、Docker 入口都要显式启动三件套；Windows 官方预编译 FrankenPHP 无法内置自定义 Caddy 模块 | 在 Linux 定制构建的 xcaddy 模块清单加入 `github.com/abiosoft/caddy-exec`（锁定版本）；Caddy 全局 startup 钩子调用启动脚本拉起 mysql / redis（钩子内部仍走 `bin/frampp start mysql redis`，维持 PID 文件与状态一致），shutdown 钩子在 Caddy 退出时回收 mysql / redis；`frampp start`、安装器与容器入口相应简化。实施前需验证：Caddyfile 语法、reload 时是否重复执行、优雅退出（SIGTERM）与强杀（SIGKILL）场景下 shutdown 钩子的可靠性 |
| 9 | 独立插件项目 `caddy-timer`（后续版本，backlog） | 尚不存在；作为 FRAMPP 作者维护的 Caddy 模块生态延续 | 独立仓库开发定时调度 Caddy 模块：到点可执行外部脚本、发起 HTTP 请求、或调用内部 worker，并记录每次触发与执行结果（留档审计）。**排期在 v0.8.0 之后；集成门槛：插件完成后需用户明确指示，才接入 FRAMPP 定制构建；在此之前仅记录、不实施** |

## 影响面

- 打包脚本与安装器：`installer/scripts/build-linux-package.ps1`、`installer/setup.iss`；
- 运行时读取：`control-panel/bin/frampp`（`self_version()`、start 输出与退出码）、`control-panel/src/ServiceManager.php`（`start()` / `startDetached()` / 端口预检）、控制面板 `web/action.php`；
- CLI 与面板新增能力：`frampp restart` 指令、`start` 就绪轮询（`ServiceManager` / `web/action.php` / `framppd`）；
- 守护与健康检查：`framppd`、`docker-healthcheck.sh`、Dockerfile 内 docs / VERSION 路径；
- 安装脚本提示语：`installer/scripts/init.ps1`、`installer/scripts/linux/init.sh`、`frampp-installer.sh`、`bin/uninstall` 等；
- 端口策略：`installer/scripts/init.ps1`、`installer/scripts/linux/init.sh`（默认端口与占用检测）、`control-panel/src/ServiceManager.php`（`ports()` / Caddyfile 渲染）、`var/runtime.json`（`ports` 字段）、`installer/templates/Caddyfile.template`、README / 用户文档中的默认端口说明；
- caddy-exec / caddy-timer（如集成）：`installer/scripts/linux/build-frankenphp.sh`（xcaddy 模块清单）、Caddyfile 全局钩子配置、`installer/scripts/linux/init.sh`、`bin/frampp` 与 ServiceManager / framppd / Docker 入口的生命周期衔接；
- 文档互链：README ↔ docs 内链接、升级文档（旧安装目录 `docs/`、根 `VERSION` 与新 `share/docs/`、`etc/VERSION` 并存处理）。

## 验收标准

- Linux 安装后根目录仅含 `bin/`、`etc/`、`htdocs/`、`logs/`、`modules/`、`share/`、`var/`、`frampp`（符号链接）与 `LICENSE`，无根目录 `README.md` / `docs/` / `VERSION`。
- `share/docs/` 内含 README 英文版与中文版，用户文档齐全；`etc/VERSION` 存在且 `frampp version` 正确输出，旧布局（根 `VERSION`）读取回退可用。
- TCP 模式下 `frampp start`：端口被其他进程占用 → 明确报错、不误报 `started=true`；进程启动即退出 → 返回失败并附日志末行；正常启动 → `started=true`。
- `frampp restart` 可重启单个服务与全部服务，控制面板按钮 / `framppd` 行为一致；启动失败时延迟检测后明确报错且退出码非零。
- 安装 / 初始化 / 卸载脚本提示语全部为中英双语。
- 默认端口冲突时可自动 / 半自动规避（提示并改用空闲端口），`frampp ports` 与控制面板显示实际端口。
- （Linux，caddy-exec）仅拉起 FrankenPHP 时 mysql / redis 随 Caddy 启动自动就绪；Caddy 优雅退出后 mysql / redis 自动回收；`frampp status` 与 `var/*.pid` 仍准确，`frampp stop all` 与控制面板行为不受影响。
- `tests/run-tests.ps1` 全部通过；CI 冒烟（ubuntu + windows）通过。

## 未决问题

- Windows 安装向导 `isreadme` 展示源：保留根目录 README 还是改为 `share/docs/README.md`，需确认 Inno Setup 的 README 路径语义。
- Docker 镜像内是否同步调整 docs / VERSION 位置（镜像内 `/opt/frampp/docs`、`/opt/frampp/VERSION`）。
- 端口占用者识别：是否输出占用进程名（Windows `Get-NetTCPConnection` / `netstat`，Linux `ss` / `lsof`），还是仅提示端口被占用并给出排查建议。
- `restart` 语义：未运行时是否等同 start；单服务重启时的依赖顺序（先 DB/Redis 后 FrankenPHP）是否沿用 stop 的反序。
- 就绪检测阈值与重试策略（如 1s×10 次）是否可通过 `runtime.json` / 环境变量配置，以及日志“致命错误”判定规则（关键字还是退出码）。
- 端口策略取舍：固定高位端口（如 18080 / 18081）还是动态分配首个空闲端口；是否只调整对外站点端口，还是连同 Caddy admin 2019 / MySQL 3306 / Redis 6379 一并处理（后者影响 Agent 与客户端连接配置）。
- caddy-exec 与 ServiceManager 的关系：钩子脚本复用 `bin/frampp start|stop` 还是另起一套启动逻辑；Caddy reload、非优雅退出（崩溃 / SIGKILL）时 shutdown 钩子是否可靠、是否会遗留孤儿进程；该机制仅 Linux 定制构建可用，Windows 是否保持 ServiceManager 显式启停（与 caddy-access-filter 相同约束）。
- caddy-timer 的能力边界（cron 表达式语法、外部脚本 / HTTP / worker 三种触发、触发与执行记录的格式与落盘位置）与最终集成方式，待插件原型完成后评估。
