# FRAMPP v0.9.0 改进计划

> 状态：部分实施（2026-10-22）：第 1–3 项已在 v0.8.2 Linux-only 临时版实现；
> 第 8 项已在 0.8.1 提前实施；第 4–7、9–11 项待 v0.9.0 正式版
> 基线：v0.8.3（PHP 8.5.12 / FrankenPHP 1.13.2）
> 说明：承接 `docs/0.8.0-plan.md` 第 9 项（pogo-scheduler 自 fork）与本轮新增
> 六项（安装器英文优先、应用目录结构、缺省安装目录 `/opt/frampp`、非 root +

> 实施前按仓库规则在

## 改进清单

| # | 改进项 | 现状 | 计划方案 |
| --- | --- | --- | --- |
| 1 | ✅（0.8.2）一键安装器消息改为英文优先（英文默认、中文第二语言） | Windows 安装器 `installer/setup.iss` 的两条 `StatusMsg` 是硬编码中文（`正在初始化 FRAMPP 运行时...`、`正在启动服务...`），与安装器语言选择无关；Linux `.run` 安装器输出为中文在前（`==> 一键安装 / one-click install`）；init 脚本部分提示同样是中文在前 | 0.8.2 已实施：Windows 改用 Inno `[CustomMessages]` + `{cm:...}`；Linux `.run` / `init.sh` / `init.ps1` / `uninstall` 的用户可见提示统一为英文在前、中文在后（清理纯中文提示） |
| 2 | ✅（0.8.2）应用目录结构：新增 application/apps 目录，`htdocs` 下移一级，避免后台代码/配置落入 Web 根 | Docker 直接以 `/opt/frampp/htdocs` 作为站点根并挂为卷（`Dockerfile` `VOLUME`、`docker-compose.yml` `frampp-htdocs:/opt/frampp/htdocs`）；用户若把后台 PHP、配置文件、`vendor/` 放进 htdocs，会被 Web 直接暴露；安装包布局同样只有单一 `htdocs/` | 0.8.2 已实施：`apps/<app>/{htdocs,config,src,var}`（默认 `apps/default`）；Docker 新增 `frampp-apps` 卷（保留旧 htdocs 兼容卷）；Caddyfile 默认站点、`frampp new-project`、站点管理默认 root 同步；旧 htdocs 自动迁移/兼容链接 |
| 3 | ✅（0.8.2）集成 pogo-scheduler 自 fork（`wangbo5825/scheduler`）定时调度（承接 v0.8.0 计划第 9 项） | `pogo/scheduler` 为 Caddy / FrankenPHP 嵌入式 cron 触发模块（Go ticker，按墙钟整分触发外部命令）；尚无可用于 FRAMPP 的自 fork 版本 | 0.8.2 已实施：Linux 定制构建加入 `github.com/wangbo5825/scheduler/module@e492454`（v0.1.0，按 commit 固定）；`etc/scheduler.caddy`（默认关闭）通过 import 注入全局配置，支持 HTTP / command 两种任务与 interval/cron；事件写入 FrankenPHP 日志；CI 冒烟验证模块存在与实际 HTTP 触发 |
| 4 | Linux 缺省安装目录改为 `/opt/frampp` | `.run` 安装器缺省安装到 `~/frampp`（`DEFAULT_PREFIX="${HOME:-.}/frampp"`），文档示例也以 `~/frampp` 为默认、把 `/opt/frampp` 写成“自定义目录”；与 LAMPP（`/opt/lampp`）传统和 FRAMPP Docker 镜像（`/opt/frampp`）不一致 | Linux 一键安装包缺省前缀改为 `/opt/frampp`（对齐 LAMPP 与 Docker）；`/opt` 需要 root，安装器在非 root 且未显式给出 `--prefix` 时提权或给出明确指引，保留 `--prefix` 供非 root 安装（如 `~/frampp`）；同步更新安装提示与 usage、README（中英）与 docs/user、升级/卸载说明、systemd 单元示例（`__FRAMPP_HOME__` → `/opt/frampp`）与 CI 冒烟说明（CI 继续用 `--prefix` 到临时目录） |
| 5 | 非 root 运行 FRAMPP：用 `setcap` 授予绑定 80 / 443 的能力 | 服务进程目前以启动用户身份运行；默认站点/控制台绑定 127.0.0.1:8080/8081（非特权端口）不涉及权限问题，但要让站点监听 80 / 443（需求 4 的非 root 场景）就需要 `CAP_NET_BIND_SERVICE` | 保持**非 root 运行**：为 FrankenPHP 可执行文件（内嵌 Caddy）配置文件能力 `sudo setcap cap_net_bind_service=+ep <FRAMPP_HOME>/modules/frankenphp/frankenphp`；提供 `bin/frampp cap install\|remove\|status` 辅助命令与升级后自动重施（`.run` 覆盖二进制会丢能力）；systemd 场景优先用单元片段 `AmbientCapabilities=CAP_NET_BIND_SERVICE` + `CapabilityBoundingSet=CAP_NET_BIND_SERVICE`（无需 setcap）；Docker 用 `--cap-add=NET_BIND_SERVICE`；文档补充 `net.ipv4.ip_unprivileged_port_start=80` 作为替代方案与各自取舍 |
| 6 | 启动脚本支持 chroot / 沙箱，限制 PHP 访问其他目录 | `php` 处理器以运行用户身份执行站点 PHP，可读取文件系统上运行用户可访问的任意路径；当前仅靠 localhost 绑定与只读数据库账号，没有文件系统隔离 | 提供可选的隔离启动模式（默认关闭，不改变现有行为）：优先推荐 systemd 沙箱（`RootDirectory=` / `ProtectSystem=strict` / `ProtectHome=yes` / `ReadWritePaths=<FRAMPP_HOME>/var,logs,htdocs` / `PrivateTmp=yes` / `NoNewPrivileges=yes`）与 rootless 方案（`bwrap` / user namespace），其次提供 `bin/frampp start --chroot`（需 root / `CAP_SYS_CHROOT`，仅对 FrankenPHP 生效，MySQL/Redis 保持隔离外并注意 socket 可见性）；同时为站点生成 PHP `open_basedir`（限定 `htdocs/` 与上传临时目录）作为无特权兜底；新增 `docs/user/security.md` 说明边界与取舍；需求 5（非 root）与 root chroot 存在张力，默认仍走“非 root + systemd 沙箱 / open_basedir” |
| 7 | 上传内容不得为 PHP / 可执行代码，避免上传非法内容被当作 Web 代码执行 | 站点根即 `htdocs/`，`php` 处理器对根下所有 PHP 文件生效；用户应用若把上传文件落在 Web 根内的 `uploads/` 一类目录，攻击者可上传 `.php` / `.phtml` / `.phar` 等文件形成 webshell；当前 PHP 与 Caddy 配置均无“上传目录不执行脚本”的约束，也无上传大小/类型策略 | 三层防护：① **存储位置**：默认上传目录放在 Web 根之外（与需求 2 的 `apps/<app>/var/uploads` 配合），只能由应用代码受控读取并回传，杜绝直接访问与执行；② **Web 层**：Caddyfile 模板 / 站点片段对上传路径与可执行扩展（`.php`/`.phtml`/`.phar`/`.php3`/`.php5`/`.pht` 等）显式禁用 `php` 处理器，仅静态或直接 403（兼容用户把 uploads 放在 htdocs 内的既有站点）；③ **应用层**：`php.ini` 模板补充 `upload_max_filesize` / `post_max_size` / `max_file_uploads` 与 `file_uploads` 策略，项目模板给出安全上传示例（随机化文件名、扩展名与 MIME 白名单、`move_uploaded_file` 后校验、必要时内容魔数检查）；控制面板 / caddy-panel 的导入能力（证书 PEM/KEY、站点文件包）同样只接受白名单类型与大小并拒绝路径穿越、可执行代码 |
| 8 | xcaddy 模块全部锁定版本，保证跨架构构建可复现（**0.8.1 已提前实施**） | 0.8.1 的 arm64 全新构建解析到 **Caddy v2.11.7**，而 x86_64 复用旧缓存时仍是 v2.11.4；根因是 `build-frankenphp.sh` 中 `github.com/dunglas/caddy-cbrotli` 与 `github.com/darkweak/storages/otter/caddy` 未固定版本（xcaddy 取最新，MVS 会抬升 Caddy 版本） | ✅ 0.8.1：`caddy-cbrotli@v1.0.1`、`storages/otter/caddy@v0.0.20` 已固定，构建缓存标记升级为 `-modpins1` 强制两架构重建；冒烟改为断言 Caddy ≥ 2.11.4 并打印实际版本。剩余：把 Caddy 版本写入 Release note / `runtime.json` 作为可追溯记录 |
| 9 | 升级 scheduler 插件 v0.1.0 → **v0.2.0**，支持多个独立定时器 | 0.8.3 锁定 `github.com/wangbo5825/scheduler/module@e492454`（v0.1.0）；全局 `pogo_scheduler` 配置只能定义一组顶层任务参数，无法在同一 Caddyfile 中表达多个独立定时任务 | v0.9.0 将模块固定到 **v0.2.0 tag 对应 commit `2c8552504066cd276b704b7e6cc357405ef1b84b`**（Go module 位于仓库 `module/` 子目录，继续按 commit 固定）。使用 `job <name> { ... }` 配置多个 HTTP / command 定时器，每个任务独立维护 interval / cron、timeout、overlap 和 shutdown 生命周期；保留 v0.1.0 顶层单任务语法以兼容旧配置，但禁止在同一 `pogo_scheduler` 块中混用顶层任务参数和 `job` 块。同步更新缓存标记、默认示例、中英文 scheduler 文档，并增加两个不同周期任务的独立触发冒烟（其中一个任务运行中不得阻止另一个任务） |
| 10 | **Bug**：部分 Linux 环境启动 MySQL 时报缺少 `libaio.so.1`；首次初始化失败后可能出现数据目录为空，当前错误信息不足以定位和修复 | MySQL 8.0 通用二进制动态依赖 `libaio.so.1`；现在仅在文档中要求另行安装 `libaio` / `libaio1`，而 Ubuntu 24.04+ / Debian 13 等 t64 发行版通常只提供 `libaio.so.1t64`。`libnuma.so.1` 可能按二进制链接方式成为另一项缺失依赖，必须通过实际 `ldd` / `DT_NEEDED` 检查确认。非 root 安装、精简容器或未安装兼容包的机器会在启动阶段直接失败，常见错误为 `error while loading shared libraries: libaio.so.1: cannot open shared object file`。当前 `init.sh` 在 `mysqld --initialize-insecure` 失败后只输出警告并继续，可能让安装表面完成、后续才发现数据目录为空或 `db_initialized=0`。现场曾手工执行 `mysqld --initialize --user=<user> --datadir=<FRAMPP_HOME>/modules/mysql/data`；但 FRAMPP 的正常数据目录是 **`var/mysql`**，手工初始化 `modules/mysql/data` 只会创建一个 ServiceManager 不会使用的数据目录，不能作为正式恢复步骤 | ① 安装 / `init` / `frampp start mysql` 增加 ELF `DT_NEEDED` + `ldd` 启动前自检，分别报告 `libaio.so.1`、`libnuma.so.1` 等缺失项；② 探测 `libaio.so.1`、`libaio.so.1t64` 是否存在，缺包时输出当前发行版对应的安装命令与说明；③ 初始化失败必须立即非零退出，并同时打印 `mysql-init.log`、当前 `DATADIR`、`db_initialized`，禁止仅警告后继续；④ 增加 `frampp db status/doctor` 输出权威目录 `var/mysql`、`runtime.json` 标记及是否含 `mysql.ibd`，检测到 `modules/mysql/data` 等非标准目录时提示迁移或重新执行 `bin/frampp init`；⑤ 优先把兼容库 / shim 放入 FRAMPP 自有库目录并以受控库路径加载，不静默修改系统 `/usr/lib`；⑥ 新增最小容器 / t64 环境冒烟，覆盖缺包 fail-fast、安装依赖后 `bin/frampp init` 成功，以及手工错误目录不会被视为已初始化 |
| 11 | **Bug**：部分 CSS 请求返回 `Content-Type: text/html`，浏览器拒绝应用样式 | 默认站点、控制面板和 `/panel` 路由均使用 `try_files {path} {path}/index.php index.php`；请求不存在的静态文件或不匹配实际挂载路径的 CSS 时会回退到 PHP/HTML，状态可能为 200 且 MIME 为 `text/html`，而不是 CSS 或 404。现有 CI 只检查页面 HTML，未校验静态资源 MIME | 在 SPA/PHP fallback 前增加静态资源短路路由，覆盖 `.css`、`.js`、字体、图片、sourcemap 等扩展名：命中文件时只交给 `file_server`，缺失时返回 404，禁止回退到 `index.php`；确保 `.css` 返回 `text/css`（可带 charset）；同时审查默认站点、平台控制台和 `/panel` 的 root / `handle_path` 映射。CI 新增正反向断言：真实 CSS 为 200 + `text/css`，不存在的 CSS 为 404 且不得返回 `text/html` 页面 |

## 优先级与范围

第 4、5、6、7、9、10、11 项纳入 v0.9.0；第 1–3 项已在 0.8.2/0.8.3 提前完成，
第 8 项已在 0.8.1 完成。scheduler v0.2.0 升级是 0.1.0 集成的后续增强，不改变默认关闭
策略；第 10、11 项为明确缺陷修复，应优先于新增功能完成。
跨平台行为在 Windows + Linux CI 中验证（Windows 安装目录保持
`C:\Program Files\FRAMPP` 不变；第 5、6 项为 Linux 特性，Windows 侧给出等价说明或
明确不支持）。

## 验收标准

- Windows 一键安装器在英文环境下的进行中提示为英文（切中文语言时为中文），
  Linux `.run` / init 输出英文在前、中文在后且无纯中文提示残留；
- 全新安装（含 Docker）默认生成应用目录：`apps/<app>/htdocs` 为 Web 根，
  `config/`、`src/`、`var/` 位于其上一级且不可通过 HTTP 访问；
- `frampp new-project` 与 `/panel` 站点管理创建的站点落在 `apps/<app>/htdocs`；
- Docker 卷改为应用目录后，容器重建数据不丢；文档给出旧 `htdocs/` 迁移步骤；
- Linux 一键安装不带 `--prefix` 时缺省安装到 `/opt/frampp`（对齐 Docker 与 LAMPP），
  非 root 场景有明确的提权或指引；`--prefix ~/frampp` 等自定义安装仍可用，文档示例一致；
- 第 5 项：非 root 用户执行 `bin/frampp cap install` 后，站点可直接监听 80 / 443；
  binary 能力随升级自动重施；`cap status` 可自检；systemd 场景用 AmbientCapabilities
  即可，无需 setcap；文档明确“文件能力 + 可写二进制 = 提权风险”，要求二进制归 root
  所有且对运行用户只读；
- 第 6 项：可选的隔离启动模式生效后，站点 PHP 无法读取 `apps/<app>/htdocs`（与显式
  允许的路径）之外的文件；默认配置行为不变；`open_basedir` 生成可被独立验证；
  `docs/user/security.md` 说明 chroot / systemd 沙箱 / rootless 三种方案的边界与限制；
- 第 7 项：默认上传目录位于 Web 根之外；即使站点把 `uploads/` 放在 `htdocs/` 内，
  通过 HTTP 请求其中的 `.php` / `.phtml` / `.phar` 等文件也不会被执行（403 或静态/拒绝），
  CI 冒烟覆盖该断言；`php.ini` 上传大小与数量限制生效；控制面板 / caddy-panel 的导入
  仅接受白名单类型并拒绝可执行内容；文档给出既有站点的加固与迁移指引；
- 若第 3 项落地：Linux 定制构建含 scheduler 模块，定时任务可按配置触发并留档，
  `frampp` 能查看调度记录；Windows 行为有明确说明。
- 第 9 项：Linux 定制 FrankenPHP 锁定 scheduler v0.2.0；同一
  `pogo_scheduler { job ... job ... }` 配置中的两个任务按各自周期独立触发，
  单个任务占用或超时不会阻塞其它任务；旧 v0.1.0 顶层单任务配置仍能通过 `caddy adapt`
  与启动冒烟；中英文文档包含多任务示例和 0.1.0 → 0.2.0 迁移说明。
- 第 10 项：缺少 `libaio.so.1` 时，安装或启动在尝试拉起 MySQL 前返回非零状态和明确的
  OS / 架构对应安装指引，不再只留下通用启动失败；存在 `libaio.so.1t64` 时可通过
  FRAMPP 自有兼容路径成功启动；`mysqld --initialize` 失败时 `bin/frampp init` 必须立即
  非零退出，并明确显示权威数据目录为 `var/mysql`；`modules/mysql/data` 等非标准目录
  不得被误报为数据库已初始化；MySQL 正常环境不得因自检产生新依赖。
- 第 11 项：默认站点、8081 控制台和 `/panel` 下真实 `.css` 均返回 HTTP 200 且
  `Content-Type: text/css`；不存在的 `.css` 返回 404，不得回退为 `text/html`；
  默认站点页面至少有一个外部 CSS 资源纳入 CI 实际请求验证。
