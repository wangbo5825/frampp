# FRAMPP v0.9.0 改进计划

> 状态：计划中（2026-09-12）
> 基线：v0.8.0
> 说明：承接 `docs/0.8.0-plan.md` 第 9 项（pogo-scheduler 自 fork）与本轮新增
> 五项（安装器英文优先、应用目录结构、缺省安装目录 `/opt/frampp`、非 root +
> setcap 绑定 80/443、启动 chroot / 沙箱隔离）；实施前按仓库规则在
> `docs/blueprint.md` 补决策记录。

## 改进清单

| # | 改进项 | 现状 | 计划方案 |
| --- | --- | --- | --- |
| 1 | 一键安装器消息改为英文优先（英文默认、中文第二语言） | Windows 安装器 `installer/setup.iss` 的两条 `StatusMsg` 是硬编码中文（`正在初始化 FRAMPP 运行时...`、`正在启动服务...`），与安装器语言选择无关；Linux `.run` 安装器输出为中文在前（`==> 一键安装 / one-click install`）；init 脚本部分提示同样是中文在前 | Windows：改用 Inno `[CustomMessages]`（`english.` / `chinesesimplified.`）并在 `StatusMsg` 用 `{cm:...}`，使提示跟随安装器语言、默认英文；Linux：`frampp-installer.sh`、`installer/scripts/linux/init.sh`、`installer/scripts/init.ps1` 的用户可见提示统一改为**英文在前、中文在后**，并清理残留纯中文提示（保留内部注释中文）；可选支持 `FRAMPP_LANG=zh` 一类开关 |
| 2 | 应用目录结构：新增 application/apps 目录，`htdocs` 下移一级，避免后台代码/配置落入 Web 根 | Docker 直接以 `/opt/frampp/htdocs` 作为站点根并挂为卷（`Dockerfile` `VOLUME`、`docker-compose.yml` `frampp-htdocs:/opt/frampp/htdocs`）；用户若把后台 PHP、配置文件、`vendor/` 放进 htdocs，会被 Web 直接暴露；安装包布局同样只有单一 `htdocs/` | 引入应用目录约定：`apps/<app>/{htdocs/, config/, src/, var/}` —— **只有 `htdocs/` 是 Web 根**，其余位于其上一级（不可从 Web 访问）。Docker：卷改为挂载应用目录（如 `frampp-apps:/opt/frampp/apps`），`htdocs` 作为其中一个子目录；Caddyfile / 站点管理（caddy-panel `/panel`）、`frampp new-project`、项目模板、用户文档与升级说明同步适配；保留旧 `htdocs/` 兼容（首次初始化时迁移或提示） |
| 3 | 集成 pogo-scheduler 自 fork（`wangbo5825/scheduler`）定时调度（承接 v0.8.0 计划第 9 项） | `pogo/scheduler` 为 Caddy / FrankenPHP 嵌入式 cron 触发模块（Go ticker，按墙钟整分触发外部命令）；尚无可用于 FRAMPP 的自 fork 版本 | 维护自 fork 并接入 Linux 定制构建的 xcaddy 模块清单：到点执行外部脚本 / 发起 HTTP 请求 / 调用内部 worker，并记录每次触发与执行结果（留档审计）；**集成门槛：fork 就绪且明确指示后实施**；Windows 官方构建不含自定义模块，行为由 ServiceManager/外部调度兜底 |
| 4 | Linux 缺省安装目录改为 `/opt/frampp` | `.run` 安装器缺省安装到 `~/frampp`（`DEFAULT_PREFIX="${HOME:-.}/frampp"`），文档示例也以 `~/frampp` 为默认、把 `/opt/frampp` 写成“自定义目录”；与 LAMPP（`/opt/lampp`）传统和 FRAMPP Docker 镜像（`/opt/frampp`）不一致 | Linux 一键安装包缺省前缀改为 `/opt/frampp`（对齐 LAMPP 与 Docker）；`/opt` 需要 root，安装器在非 root 且未显式给出 `--prefix` 时提权或给出明确指引，保留 `--prefix` 供非 root 安装（如 `~/frampp`）；同步更新安装提示与 usage、README（中英）与 docs/user、升级/卸载说明、systemd 单元示例（`__FRAMPP_HOME__` → `/opt/frampp`）与 CI 冒烟说明（CI 继续用 `--prefix` 到临时目录） |
| 5 | 非 root 运行 FRAMPP：用 `setcap` 授予绑定 80 / 443 的能力 | 服务进程目前以启动用户身份运行；默认站点/控制台绑定 127.0.0.1:8080/8081（非特权端口）不涉及权限问题，但要让站点监听 80 / 443（需求 4 的非 root 场景）就需要 `CAP_NET_BIND_SERVICE` | 保持**非 root 运行**：为 FrankenPHP 可执行文件（内嵌 Caddy）配置文件能力 `sudo setcap cap_net_bind_service=+ep <FRAMPP_HOME>/modules/frankenphp/frankenphp`；提供 `bin/frampp cap install\|remove\|status` 辅助命令与升级后自动重施（`.run` 覆盖二进制会丢能力）；systemd 场景优先用单元片段 `AmbientCapabilities=CAP_NET_BIND_SERVICE` + `CapabilityBoundingSet=CAP_NET_BIND_SERVICE`（无需 setcap）；Docker 用 `--cap-add=NET_BIND_SERVICE`；文档补充 `net.ipv4.ip_unprivileged_port_start=80` 作为替代方案与各自取舍 |
| 6 | 启动脚本支持 chroot / 沙箱，限制 PHP 访问其他目录 | `php` 处理器以运行用户身份执行站点 PHP，可读取文件系统上运行用户可访问的任意路径；当前仅靠 localhost 绑定与只读数据库账号，没有文件系统隔离 | 提供可选的隔离启动模式（默认关闭，不改变现有行为）：优先推荐 systemd 沙箱（`RootDirectory=` / `ProtectSystem=strict` / `ProtectHome=yes` / `ReadWritePaths=<FRAMPP_HOME>/var,logs,htdocs` / `PrivateTmp=yes` / `NoNewPrivileges=yes`）与 rootless 方案（`bwrap` / user namespace），其次提供 `bin/frampp start --chroot`（需 root / `CAP_SYS_CHROOT`，仅对 FrankenPHP 生效，MySQL/Redis 保持隔离外并注意 socket 可见性）；同时为站点生成 PHP `open_basedir`（限定 `htdocs/` 与上传临时目录）作为无特权兜底；新增 `docs/user/security.md` 说明边界与取舍；需求 5（非 root）与 root chroot 存在张力，默认仍走“非 root + systemd 沙箱 / open_basedir” |

  `installer/scripts/init.ps1`、`bin/uninstall`；

  root/`--prefix` 处理）、`installer/runtime/frampp.service.template`、
  `README.md` / `README.zh-CN.md`、`docs/user/*`（安装 / 升级 / Docker 示例）；
- 非 root / setcap（第 5 项）：`bin/frampp`（`cap` 子命令）、`installer/scripts/linux/init.sh`

## 优先级与范围

第 1、2、4、5、6 项纳入 v0.9.0；第 3 项（pogo-scheduler 自 fork）以 fork 就绪为
前提，就绪即可随 v0.9.0 一起发布，否则顺延。跨平台行为在 Windows + Linux CI 中
验证（Windows 安装目录保持 `C:\Program Files\FRAMPP` 不变；第 5、6 项为 Linux 特性，
Windows 侧给出等价说明或明确不支持）。

## 验收标准

- Windows 一键安装器在英文环境下的进行中提示为英文（切中文语言时为中文），
  Linux `.run` / init 输出英文在前、中文在后且无纯中文提示残留；
- 全新安装（含 Docker）默认生成应用目录：`apps/<app>/htdocs` 为 Web 根，
  `config/`、`src/`、`var/` 位于其上一级且不可通过 HTTP 访问；
- `frampp new-project` 与 `/panel` 站点管理创建的站点落在 `apps/<app>/htdocs`；
- Docker 卷改为应用目录后，容器重建数据不丢；文档给出旧 `htdocs/` 迁移步骤；
- Linux 一键安装不带 `--prefix` 时缺省安装到 `/opt/frampp`（对齐 Docker 与 LAMPP），
  非 root 场景有明确的提权或指引；`--prefix ~/frampp` 等自定义安装仍可用，文档示例一致；
- 第 5 项：非 root 用户执行 `bin/frampp cap install` 后，站点可直接监听 80 / 443；
  binary 能力随升级自动重施；`cap status` 可自检；systemd 场景用 AmbientCapabilities
  即可，无需 setcap；文档明确“文件能力 + 可写二进制 = 提权风险”，要求二进制归 root
  所有且对运行用户只读；
- 第 6 项：可选的隔离启动模式生效后，站点 PHP 无法读取 `apps/<app>/htdocs`（与显式
  允许的路径）之外的文件；默认配置行为不变；`open_basedir` 生成可被独立验证；
  `docs/user/security.md` 说明 chroot / systemd 沙箱 / rootless 三种方案的边界与限制；
- 若第 3 项落地：Linux 定制构建含 scheduler 模块，定时任务可按配置触发并留档，
  `frampp` 能查看调度记录；Windows 行为有明确说明。

## 未决问题

- 目录命名与位置：`apps/` 还是 `applications/`、放在安装根还是 `var/` 旁；
  是否允许应用目录整体移动（与“目录可整体移动”承诺的关系）；
- 旧安装（≤0.8.0）的 `htdocs/` 迁移策略：自动迁移、首次启动提示还是仅文档说明；
- 站点根与 `frampp new-project` 的默认路径/模板结构（是否引入 `public/` 与
  `htdocs/` 双层约定）；
- `FRAMPP_LANG` 类语言开关的命名与优先级，是否与 caddy-panel 的 `--lang=zh` /
  `CADDY_PANEL_LANG` 保持一致；
- `/opt/frampp` 的权限处理：自动 `sudo` 提权重执行、还是提示用户手动以 root 运行；
  非 root 环境是否保留 `~/frampp` 作为回退缺省值，以及旧安装（`~/frampp`）升级时的提示方式；
- Windows 是否同步调整默认目录（当前 `C:\Program Files\FRAMPP`），或仅 Linux 对齐 `/opt`；
- 第 5 项路径选择：文件能力（setcap）还是 systemd `AmbientCapabilities`（推荐），
  或 `net.ipv4.ip_unprivileged_port_start`；setcap 与 UPX 压缩 / musl 静态二进制的
  兼容性与升级重施时机（`init` / `upgrade` / 包管理器钩子）；
- 第 6 项实现边界：只隔离 FrankenPHP 还是包含 MySQL/Redis（socket 可见性与性能影响）；
  root chroot（需要 `CAP_SYS_CHROOT`，与第 5 项“非 root”目标冲突）与 rootless
  user namespace / systemd 沙箱的优先级；`open_basedir` 的绕过风险与站点可写目录
  （上传、缓存、`var/`）白名单策略；与 caddy-panel 证书存储（443）和 `apps/` 布局
  （需求 2）的配合；
- scheduler fork 的模块 ID / 配置键 / 审计记录格式（与 caddy-access-filter 风格对齐）。
